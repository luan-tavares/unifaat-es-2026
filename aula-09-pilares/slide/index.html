Getter e setter: a porta controlada

src/09/encapsulamento.py
@property
def nome(self): # getter
return self.__nome
@nome.setter
def nome(self, novo_nome): # setter
self.__validar_nome(novo_nome)
self.__nome = novo_nome
@property
def pai(self): # só getter
return self.__pai
combinaçãopermite
getter + setter com validaçãoler e escrever, com regra
só gettersó ler (item.pai = x dá erro)

Quem usa continua escrevendo item.nome. O encapsulamento mais forte nem libera setter: expõe o que o objeto faz, não o dado cru.

Antes dos pilares: o que é abstrair?

Do latim abstrahere, "arrastar para fora, separar": recortar o essencial e ignorar o detalhe. Não é inventar, é recortar.

# o que eu uso (interface)
mapa do metrô: estações e ligações
dirigir: volante, pedais, câmbio
Explorador: pastas e arquivos
# o que ignoro (implementação)
as ruas, as curvas, as distâncias
a combustão, a injeção
setores de disco, blocos, ponteiros

O ganho é sempre o mesmo: usar sem precisar entender tudo. Guarde a frase: ela volta em cada pilar.

pilar 1

Encapsulamento: dados privados, porta pública

  • Agrupar dados e métodos e controlar o acesso: __, property, __slots__
  • Caixa eletrônico: você usa sacar(), não mexe no saldo
  • A classe pode mudar por dentro sem quebrar quem a usa

Abstração aqui: separa a interface (mover_para()) da implementação (__filhos).

▶ Diagrama vivo: aula-09-pilares/modelos/encapsulamento/index.html
pilar 2

Herança: o geral e o específico

  • Relação "é um": Pasta é um Item, Arquivo é um Item; cada filha lista só o que acrescenta
  • Acoplamento forte: só com "é um" de verdade. "Tem um" é composição (a pasta tem filhos)
  • _receber() protegido: o que a filha enxerga (e sobrescreve) da mãe

Abstração aqui: separa o geral (Item) do específico (Pasta, Arquivo).

▶ Diagrama vivo: aula-09-pilares/modelos/heranca/index.html
pilar 3

Polimorfismo: a mesma chamada, formas diferentes

  • filho.tamanho() serve para pasta e arquivo, sem if eh_pasta
  • Override: a filha redefine o método e o Python escolhe em execução. Python não tem overload
  • Sem herança também vale: duck typing (quem tem tamanho() serve)

Abstração aqui: separa o que se pede (tamanho()) de como é feito (cada classe calcula).

Nos três, o movimento é o mesmo: ignorar o detalhe para trabalhar com o essencial. A abstração não está ao lado dos pilares: está misturada dentro de cada um.

Interface: a tomada da parede

# a tomada
tem um formato (os furos, a voltagem)
não sabe o que vai ser ligado:
abajur, carregador, liquidificador
# o aparelho
segue o mesmo formato de plugue
não sabe de onde vem a energia:
hidrelétrica, painel solar, gerador

Os dois se entendem pelo contrato: o formato do plugue.

Interface é só a lista de métodos, sem estado e sem implementação: diz o que, nunca como.

Nos três pilares, a abstração aparece misturada. Na interface, ela aparece nua.

São 3 ou 4 pilares?

  • A abstração é um pilar (tem manifestação própria na interface) ou o chão onde os outros três se apoiam?
  • O encapsulamento é recurso da linguagem ou ideia de projeto? O Python tem a ideia sem o recurso e dá para ir apertando a cerca
  • 3 ou 4 são ambos válidos na literatura: nomear a abstração ajuda a nomear o raciocínio

A conclusão é de cada um. Python é OO no modelo e permissivo na disciplina: não é OO, ou só não me obriga a ser?
