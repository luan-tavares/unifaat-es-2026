1 - Introdução

Nas últimas cinco aulas, o curso construiu uma base inteira, passo a passo: entendemos por que essa disciplina se chama Engenharia de Software e não apenas Programação, vimos o que é um sistema operacional e como ele se organiza em camadas, instalamos um Linux de verdade dentro do Windows usando o WSL, descemos até o nível mais cru da máquina para entender bits, bytes e o sistema binário, aprendemos os primeiros comandos de terminal, e fechamos com Git e GitHub, versionando um projeto local e enviando esse histórico para a internet.

Esta aula não traz nenhum conceito novo. Ela existe para amarrar essas cinco aulas numa linha só, revisando com calma cada bloco, na ordem em que foram vistos, com atenção redobrada para os três pontos que mais concentram comando prático e detalhe técnico, e que também são os que mais aparecem em prova: a instalação do WSL, os binários que já foram instalados ao longo do curso, e o Git, do primeiro commit local até o push para o GitHub.

2 - O fio condutor: programar não é o mesmo que fazer engenharia

Vale relembrar o ponto que abriu o curso. Programar é a habilidade de escrever instruções que um computador executa, uma habilidade técnica e individual que qualquer pessoa aprende o básico em poucas horas. Engenharia, em qualquer área, é a disciplina de construir coisas que continuam funcionando quando outras pessoas mexem nelas, quando o tempo passa, quando o sistema cresce e quando as coisas dão errado, da mesma forma que uma ponte não é projetada só para não cair no dia da inauguração, e sim para resistir a anos de uso.

O termo Engenharia de Software nasceu em 1968, numa conferência organizada pela OTAN, durante a chamada crise do software, quando projetos estouravam prazo e orçamento e muitos simplesmente não funcionavam quando entregues. O problema não era falta de gente que soubesse programar, era falta de disciplina, processo e responsabilidade.

Mas essa palavra, engenharia, não apareceu no curso só nesse sentido de robustez ao longo do tempo — ela também descreveu, o semestre inteiro, a postura de entender o porquê das coisas antes de simplesmente usá-las. Foi por isso que se dedicou uma aula inteira a bits, bytes e sistema binário antes de qualquer sistema de verdade: entender o que o computador realmente enxerga por baixo de tudo não é enrolação, é a fundação sem a qual o resto não se sustenta. E foi essa mesma postura que explicou, por exemplo, por que o comando cd não é um binário como os outros, e sim embutido no shell: por trás de cada escolha técnica existe sempre uma razão de engenharia, nunca é só porque sim. Revisar este semestre é revisar as duas faces dessa palavra: construir para durar, e entender antes de construir.

É essa provocação de 1968, somada a essa postura de entender o porquê, que organiza o curso: o primeiro semestre responde onde e como o código roda, com sistema operacional, terminal, Linux via WSL e Git e GitHub; o segundo semestre responde como organizar o que se constrói para não virar caos, com Python, orientação a objetos e boas práticas.

3 - Sistema operacional e suas camadas

Todo computador precisa de um programa especial entre o usuário e o hardware, que só entende sinais elétricos brutos: o Sistema Operacional. Ele gerencia memória, decidindo o que cada programa pode usar, gerencia processos, decidindo o que roda e quando, e gerencia arquivos, organizando o que está salvo e onde. Windows, macOS e Linux resolvem esse mesmo problema de formas diferentes, e o curso usa Linux porque é o sistema que move a maior parte da internet, servidores e infraestrutura de nuvem.

Dentro de um sistema operacional existem três camadas que vale muito revisar. O kernel é o núcleo, a parte mais próxima do hardware, responsável por memória, processos e dispositivos, e praticamente ninguém o vê diretamente. No Linux é o kernel Linux, mantido de forma aberta e colaborativa; no Windows é o Windows NT Kernel, fechado e mantido só pela Microsoft; no macOS é o Darwin, baseado em XNU, mantido pela Apple.

A distro, abreviação de distribuição, é um conceito exclusivo do mundo Linux: como o kernel é aberto, várias organizações pegam o mesmo kernel e montam por cima um pacote completo, com gerenciador de arquivos, programas padrão e forma de instalar aplicativos. Ubuntu, Debian e Fedora são exemplos de distros, todas compartilhando o mesmo kernel Linux mas entregando experiências diferentes. O curso usa Ubuntu. Vale reforçar que Windows e macOS não têm esse conceito, porque são pacotes únicos e fechados que terceiros não podem remontar — essa é uma pegadinha clássica de prova.

A GUI, Graphical User Interface, é a camada visual, janelas, ícones, botões e mouse, intuitiva justamente porque foi desenhada para não exigir conhecimento técnico. No Linux ela é modular e escolhível, com GNOME, KDE e outras opções; no Windows e no macOS ela vem integrada e praticamente inseparável do sistema. Por fim, a CLI, Command Line Interface, popularmente chamada de terminal, é a forma de usar o computador digitando comandos de texto em vez de clicar, e não depende de nenhuma das camadas visuais anteriores.

4 - Por que o terminal importa

Vale relembrar por que o curso insiste tanto em terminal. A interface gráfica não é gratuita: toda aquela camada de janelas, ícones e animações consome memória e processamento só para existir na tela, antes mesmo de qualquer coisa útil acontecer. O terminal fala diretamente com o sistema, sem essa camada extra, o que o torna mais rápido e mais leve. Mas a razão mais importante para um desenvolvedor não é a velocidade, é que comandos de terminal podem ser repetidos e automatizados, uma coisa que um clique de mouse não permite com a mesma facilidade. Essa diferença separa usar um computador de programar. É por isso que o terminal usado no curso é sempre um terminal Linux, e não o CMD nem o PowerShell do Windows, já que é o ambiente mais usado em servidores e no mercado de trabalho, e onde ferramentas como o Git funcionam de forma mais direta.

5 - Virtualização e emulação

Para ter um terminal Linux de verdade dentro de um notebook com Windows, sem precisar trocar de sistema operacional, o curso recorreu à virtualização, a técnica que permite rodar um sistema operacional inteiro dentro de outro, como se fosse mais um programa. O sistema que já existia na máquina continua no controle total do processador, da memória e do disco, mas por cima dele é possível criar um ambiente separado, com seu próprio sistema operacional completo: a máquina virtual, ou VM.

Vale diferenciar virtualização de emulação, um conceito próximo. Emulação é quando um sistema simula o comportamento de outro sistema, geralmente com uma arquitetura de hardware diferente da original, como um emulador de Super Nintendo rodando num computador atual, que precisa traduzir em tempo real cada instrução do console antigo para o processador atual, exigindo mais processamento do que o hardware original. A virtualização, por outro lado, geralmente não exige essa tradução pesada, porque tanto a máquina virtual quanto a máquina real usam a mesma arquitetura de processador, o que a torna mais eficiente. É a virtualização, e não a emulação, que o curso usa para rodar Linux dentro do Windows.

6 - Processos

Um processo é a unidade lógica de execução de um sistema operacional, basicamente um programa em execução, com um espaço de memória próprio e um conjunto de instruções sendo processadas naquele momento. Todo programa que roda num computador existe, na prática, como um ou mais processos. Processos podem ser efêmeros, que nascem, executam uma tarefa e são encerrados logo em seguida, como um comando simples de terminal, ou permanentes, criados para continuar rodando em segundo plano por longos períodos, como serviços de sistema.

É o conjunto de processos, orquestrado pelo kernel, que faz o sistema operacional funcionar de fato, e é justamente o isolamento desses processos que torna a virtualização possível: criar uma máquina virtual é isolar um conjunto de processos e uma área de memória, de forma que esse conjunto se comporte como um sistema completo e independente, mesmo estando fisicamente dentro do mesmo hardware da máquina que já existia. Por isso um computador não deve ser pensado só como hardware mais software, ele pode abrigar outro sistema inteiro isolado rodando ao lado.

7 - A palavra binário tem mais de um sentido

Vale reforçar essa ambiguidade, porque ela costuma render questão de prova. A palavra binário aparece com sentidos diferentes ao longo do curso. No contexto de terminal, binário é o arquivo executável de um programa, o resultado final já compilado, que o sistema procura toda vez que um comando é digitado. No contexto matemático e de hardware, binário é o sistema de numeração de base 2, que usa apenas os dígitos 0 e 1. E existe ainda a ideia mais ampla de que o computador inteiro, do sistema operacional ao menor aplicativo, é, literalmente, uma sequência gigante desses mesmos 0s e 1s. Os sentidos se conectam: um arquivo executável se chama binário justamente porque, no fim, é uma sequência de 0 e 1 que o processador entende.

8 - Sistema binário e conversões

Todo processador é, fisicamente, um circuito elétrico, que só consegue distinguir com segurança dois estados, corrente passando ou não passando. É por isso que toda informação que um computador manipula precisa, em algum momento, ser traduzida para uma sequência desses dois estados, chamados de bits. Um conjunto de 8 bits forma um byte, que é sinônimo de octeto, termo mais usado em contextos de redes, como no endereçamento IP. Com n bits é possível formar dois elevado a n combinações diferentes, pela lógica do arranjo com repetição; com 8 bits, ou seja, um byte, são duas elevado a oito, ou seja, 256 combinações possíveis. Como a contagem começa do zero, essas 256 combinações representam os números de 0 a 255, e não de 1 a 256 — o maior número com n bits é sempre dois elevado a n menos 1.

O sistema binário funciona de forma posicional, igual ao sistema decimal do dia a dia, só que em base 2. No decimal, cada posição vale uma potência de 10; no binário, cada posição vale uma potência de 2, começando da direita. A tabela de posições de um byte, que vale a pena montar de cabeça antes de qualquer conta, é esta, da esquerda para a direita: dois elevado a sete vale 128, dois elevado a seis vale 64, dois elevado a cinco vale 32, dois elevado a quatro vale 16, dois elevado a três vale 8, dois elevado a dois vale 4, dois elevado a um vale 2, e dois elevado a zero vale 1. Para montar essa tabela de cabeça na hora da prova, basta começar pelo 1 na posição mais à direita e ir dobrando o valor a cada posição para a esquerda.

Para converter de binário para decimal, o caminho é: coloque cada dígito do número embaixo da tabela de posições, alinhando sempre pela direita, depois some os valores das posições onde o dígito é 1 e ignore as posições onde o dígito é 0. Primeiro exemplo: convertendo 101101 para decimal, alinhando pela direita nas posições 32, 16, 8, 4, 2 e 1, os dígitos são 1, 0, 1, 1, 0 e 1; somando as posições que têm dígito 1, ou seja, 32 mais 8 mais 4 mais 1, o resultado é 45. Segundo exemplo: convertendo 11001000 para decimal, nas oito posições de um byte, os dígitos são 1, 1, 0, 0, 1, 0, 0 e 0; somando as posições com 1, ou seja, 128 mais 64 mais 8, o resultado é 200. O erro mais comum nessa conta é alinhar o número pela esquerda em vez da direita — o último dígito, o da extrema direita, sempre vale 1 na tabela de posições, não importa o tamanho do número.

Para converter de decimal para binário existem dois caminhos, e vale saber os dois. O primeiro é a divisão sucessiva por 2: divide-se o número por 2, anota-se o resto, que só pode ser 0 ou 1, e continua-se dividindo o quociente até ele chegar a zero; o binário final é formado lendo esses restos de baixo para cima, do último resto anotado para o primeiro. Exemplo completo, convertendo 45: 45 dividido por 2 dá quociente 22 e resto 1; 22 dividido por 2 dá quociente 11 e resto 0; 11 dividido por 2 dá quociente 5 e resto 1; 5 dividido por 2 dá quociente 2 e resto 1; 2 dividido por 2 dá quociente 1 e resto 0; 1 dividido por 2 dá quociente 0 e resto 1. Lendo os restos de baixo para cima, ou seja, na ordem 1, 0, 1, 1, 0, 1, o resultado é 101101 — exatamente o mesmo número do primeiro exemplo da conversão inversa, o que confirma a conta. O erro mais comum aqui é ler os restos de cima para baixo, o que inverte o número.

O segundo caminho, de decimal para binário, é o método da tabela, por subtração, geralmente mais rápido para números até 255: pega-se a maior potência de 2 que cabe dentro do número, marca-se 1 naquela posição da tabela, subtrai-se esse valor do número, e repete-se o processo com o que sobrou; as posições que não chegam a ser usadas recebem 0. Exemplo completo, convertendo 200: o 128 cabe em 200, marca-se 1 e sobram 72; o 64 cabe em 72, marca-se 1 e sobram 8; o 32 não cabe em 8, recebe 0; o 16 não cabe em 8, recebe 0; o 8 cabe exatamente, marca-se 1 e sobra 0; o 4, o 2 e o 1 não cabem mais em nada, recebem 0. O resultado, lendo as posições de 128 até 1, é 11001000 — de novo, o mesmo número do segundo exemplo da conversão inversa.

Vale lembrar também o hexadecimal, um atalho para escrever binário de forma mais compacta, em base 16. Como 16 é uma potência de 2, dois elevado a quatro, cada dígito hexadecimal representa exatamente 4 bits, um bloco chamado de nibble, ou meio byte; os algarismos de 0 a 9 cobrem as dez primeiras combinações, e as letras de A a F cobrem as seis restantes, sendo A igual a 10 até F igual a 15. Um byte inteiro sempre cabe em exatamente dois dígitos hexadecimais, um para cada nibble. Exemplo: o byte 01000001 se divide nos nibbles 0100 e 0001, que em hexadecimal são 4 e 1, formando 41; esse mesmo 41 em hexadecimal equivale a 65 em decimal, e consultando a tabela ASCII, 65 corresponde à letra maiúscula A. É por isso que cores em código, como a cor vermelha pura, e endereços de memória costumam aparecer em hexadecimal: é uma forma compacta e fiel de escrever binário, sem perder nenhuma informação.

Esse último exemplo também mostra bem a ideia de que um byte é atômico, mas sua leitura não é: o mesmo byte 01000001 pode ser lido como o número 65, seguindo a conta de conversão, ou como a letra A, consultando a tabela ASCII, dependendo apenas do contexto que o programa aplica sobre ele — não existe um A guardado à parte na memória, existe esse número, e um programa decide interpretá-lo como caractere.

Por fim, alguns truques úteis para conferir uma conversão na hora da prova. O último dígito de um binário indica a paridade do número decimal correspondente: todo número par termina em 0, e todo número ímpar termina em 1 — se a conversão de um número ímpar terminou em 0, algo errou. Potências de 2 em binário são sempre um único 1 seguido só de zeros, como 8 igual a 1000 ou 32 igual a 100000. Números do tipo dois elevado a n menos 1 são sempre só uns, como 255 sendo oito uns seguidos, 11111111. Acrescentar um 0 à direita de um binário sempre dobra o número decimal correspondente. E o melhor teste de todos, que vale para qualquer conversão: depois de converter, faça o caminho de volta — se 45 virou 101101, some 32 mais 8 mais 4 mais 1 e confira se dá 45 de novo.

9 - WSL: instalação, hypervisor e BIOS

Retomando o WSL, Windows Subsystem for Linux, a solução que a própria Microsoft construiu para rodar uma distro Linux completa, no caso o Ubuntu, de forma leve e integrada ao Windows. Para o WSL funcionar, o processador precisa ter suporte de virtualização habilitado na BIOS, a configuração mais baixa do computador, acessada antes mesmo do sistema operacional carregar, que aparece como Virtualization Technology, ou VT-x, em processadores Intel, ou SVM Mode em processadores AMD. Esse suporte é o que permite ao hypervisor, o componente que gerencia e isola as máquinas virtuais, funcionar corretamente.

Vale relembrar o passo a passo, porque ele costuma aparecer picotado em questões de prova. Tudo começa no PowerShell do Windows, aberto como Administrador, o único momento do curso em que ainda usamos um terminal do próprio Windows. O comando wsl --install instala o WSL já na versão 2, mais performática, e já traz o Ubuntu como distro padrão, tudo de uma vez. Depois desse comando é preciso reiniciar o computador, porque o Windows precisa ativar o Hyper-V, o hypervisor usado internamente. Após reiniciar, uma janela do Ubuntu abre sozinha e pede a criação de um usuário e uma senha, que são exclusivos daquele ambiente Linux e não têm nenhuma relação com o login do Windows. Para conferir se tudo funcionou, e qual versão do WSL está rodando, existe o comando wsl --list --verbose. Caso seja preciso instalar o Ubuntu manualmente, wsl --list --online lista as distros disponíveis na loja da Microsoft, e wsl --install -d Ubuntu instala especificamente essa distro.

10 - Diretório, recursividade e os comandos do terminal

Diretório é apenas o nome técnico Linux para pasta, uma diferença só de vocabulário. Recursividade é quando uma operação se aplica a algo e depois se aplica de novo, do mesmo jeito, a cada parte menor que compõe aquilo, até não sobrar mais nada para repetir, e no contexto de diretórios isso significa que uma operação recursiva desce e repete a mesma ação em cada subdiretório.

Praticamente todo comando de terminal é, ele mesmo, um binário, no sentido explicado na seção 7: ls, mkdir, cat são arquivos executáveis que o sistema procura ao ler o que foi digitado. A exceção é o cd, que não é um binário separado, mas um comando embutido do próprio shell, o programa que interpreta os comandos, porque mudar de diretório exige alterar o estado do próprio terminal em execução, algo que um processo externo isolado não conseguiria fazer sozinho.

Vale revisar o bloco inteiro de comandos básicos: pwd mostra o caminho completo do diretório atual; ls lista arquivos e diretórios, e ls -la mostra também detalhes como permissões, dono, tamanho e data, além dos arquivos ocultos que começam com ponto; cd muda de diretório, cd sozinho volta ao diretório home do usuário, e cd .. sobe um nível; mkdir cria um diretório novo, e mkdir -p cria de uma vez uma sequência inteira de diretórios aninhados; touch cria um arquivo vazio ou atualiza sua data de modificação; cat mostra o conteúdo de um arquivo de texto na tela; cp copia um arquivo mantendo o original, e mv move ou renomeia, já que renomear é tecnicamente mover para o mesmo lugar com um nome diferente; e man abre o manual oficial de qualquer comando.

O comando rm merece atenção redobrada, porque é onde a recursividade aparece na prática e é o comando mais fácil de gerar um erro irreversível. rm apaga um único arquivo, sem passar por nenhuma lixeira. rm sozinho não apaga diretórios, e retorna erro de propósito se for usado diretamente sobre um, porque apagar um diretório inteiro é uma ação maior que exige ser solicitada explicitamente. Só com a flag recursiva, rm -r, o diretório inteiro é apagado, aplicando a remoção primeiro nos arquivos e subdiretórios mais internos, subindo nível por nível, sem nenhum aviso adicional e sem rede de segurança.

11 - O filesystem compartilhado entre WSL e Windows

O WSL cria um ambiente Linux isolado em processos e memória, mas existe uma ponte importante entre ele e o Windows: o filesystem, ou sistema de arquivos, que os dois sistemas compartilham por baixo, no mesmo disco físico. Vale relembrar o conceito de path, ou caminho, o endereço de um arquivo dentro do sistema de arquivos, a sequência de diretórios que se atravessa até chegar a ele, como um endereço postal.

Cada sistema operacional nomeia seus paths do seu próprio jeito. A pasta Área de Trabalho de um usuário no Windows tem um caminho como C, dois pontos, barra invertida, Users, barra invertida, o nome do usuário, barra invertida, Desktop. Já esse mesmo Desktop, visto de dentro do ambiente Linux do WSL, aparece como barra, mnt, barra, c, barra, Users, barra, o nome do usuário, barra, Desktop. Repare no padrão: todo o disco C do Windows aparece, dentro do WSL, montado dentro da pasta barra mnt barra c, que é a porta de entrada para o disco do Windows. Fora dessa pasta, o restante da estrutura do WSL, como a pasta pessoal do usuário Linux, é um sistema de arquivos próprio do Ubuntu, independente do Windows.

Vale reforçar também os símbolos ponto único, que representa o próprio diretório atual, e dois pontos, que representa o diretório pai, um nível acima. Esses dois símbolos existem também no Windows, e vão aparecer com frequência assim que se começa a instalar ferramentas e mover entre pastas, como no comando code ponto e no comando git add ponto, vistos a seguir.

12 - Binários de novo: instalando VS Code e Git

Cada ambiente isolado, Windows e WSL, precisa das suas próprias ferramentas instaladas, mesmo que o mesmo programa já exista do outro lado. Uma IDE, sigla de Integrated Development Environment, reúne num só programa editor de texto, terminal integrado, ferramentas de depuração e integração com Git. A IDE usada no curso é o VS Code, da Microsoft, um programa gráfico, e por isso instalado no Windows, e não dentro do WSL, já que é o Windows quem gerencia tela, mouse e janelas.

A instalação do VS Code registra, no Windows, um binário chamado code, que pode ser chamado diretamente do terminal do WSL, graças à ponte de comunicação entre os dois sistemas. O comando code ponto, digitado de dentro de qualquer pasta do Linux, abre o VS Code do Windows já apontando para aquela pasta, usando o mesmo símbolo ponto explicado na seção anterior.

O Git também precisa ser instalado nos dois ambientes, de formas diferentes. No Windows, a instalação segue o mesmo caminho do VS Code, baixando o instalador oficial no site git-scm.com. No WSL, por ser um ambiente Ubuntu, a instalação é feita pelo terminal, usando o apt, o gerenciador de pacotes padrão da distro: sudo apt update atualiza a lista de pacotes disponíveis, sudo apt install git com a flag -y instala o binário do Git de fato confirmando automaticamente qualquer pergunta, e git --version confirma que a instalação funcionou e mostra a versão instalada. Existe ainda o Vim, um editor de texto que roda inteiramente pelo terminal, sem interface gráfica, com curva de aprendizado conhecida por ser bastante íngreme, citado mas não aprofundado nesta disciplina.

13 - Git: por que versionar e como funciona

Versionar um código significa manter um histórico organizado de todas as mudanças feitas nele ao longo do tempo, quem mudou o quê e quando. Sem isso, qualquer projeto real vira, cedo ou tarde, um risco constante, já que uma alteração pequena pode quebrar uma funcionalidade que já estava funcionando, sem nenhum jeito seguro de voltar atrás.

De forma mais técnica, o Git organiza o histórico de um projeto como um grafo, mas para começar vale pensar de um jeito mais simples, como uma linha do tempo. Cada vez que se salva um progresso importante, o Git tira uma fotografia completa de como todos os arquivos estavam naquele instante, chamada de commit. Um commit não é a cópia de um arquivo isolado, é um retrato de todo o projeto naquele ponto específico, com uma mensagem explicando o que mudou desde a fotografia anterior. Por enquanto, e por todo este semestre, essa linha do tempo é sempre única e sequencial, sem desvios, já que o conceito de branch, ou ramificação, fica de fora por ora.

14 - Comandos básicos do Git e o fluxo local

Vale revisar o fluxo prático inteiro. O primeiro passo é o git init, que transforma a pasta atual num repositório Git, criando de forma escondida a pasta oculta ponto git, onde vai ser guardado todo o histórico de commits, e que só precisa ser rodado uma vez, no início do projeto. A partir daí, o git status funciona como um raio-x do momento atual do projeto, mostrando quais arquivos foram modificados, quais são novos e ainda não foram registrados, e quais já estão prontos para o próximo commit, sem nunca alterar nada.

Quando um arquivo novo é criado, ainda não é considerado parte do histórico até ser explicitamente preparado com o comando git add, que separa exatamente os arquivos que devem entrar na próxima fotografia, sendo que git add seguido de ponto prepara tudo de uma vez, todos os arquivos modificados ou novos da pasta atual. Com os arquivos preparados, o git commit, sempre acompanhado de uma mensagem escrita com a flag -m, cria de fato a fotografia do projeto no estado atual. Para visualizar essa linha do tempo formada pelos commits, existe o git log, que mostra o histórico do mais recente para o mais antigo, com o código único de identificação de cada commit, chamado de hash, o autor, a data e a mensagem. E para comparar o que mudou num arquivo antes de decidir se aquilo deve virar um commit, existe o git diff, que mostra linha a linha exatamente o que foi alterado desde o último commit.

Vale revisar também o ponteiro HEAD, que aponta sempre para o commit em que se está parado no momento, normalmente o mais recente da linha do tempo. A vantagem de usar HEAD em vez do hash de um commit é que ele pode ser combinado com uma contagem de passos para trás, como HEAD til 1, referindo-se a um commit antes do atual, HEAD til 2, dois commits antes, e assim por diante, sem precisar copiar nenhum código de commit. O comando git checkout, seguido do hash ou de HEAD e o nome de um arquivo, restaura aquele arquivo específico exatamente como ele estava naquele momento da linha do tempo, sem afetar os demais arquivos do projeto.

Além de restaurar um arquivo específico, existe uma operação mais radical, que move o próprio ponteiro HEAD para trás na linha do tempo, descartando os commits mais recentes por inteiro: o comando git reset, que tem duas variações importantes de revisar. O soft delete, feito com a flag --soft, move o ponteiro HEAD para um commit anterior, mas preserva todo o trabalho feito nos commits descartados como alterações ainda presentes nos arquivos, prontas para serem preparadas e commitadas novamente, como desfazer a fotografia mas manter tudo o que havia sido fotografado. Já o hard delete, feito com a flag --hard, move o ponteiro HEAD para um commit anterior e descarta completamente qualquer alteração feita depois dele, fazendo os arquivos voltarem exatamente ao estado anterior, sem nenhum vestígio das mudanças mais recentes, sendo por isso uma operação que deve ser usada com muita cautela, já que não existe um caminho simples de volta depois de um hard delete.

Vale lembrar que esse mesmo par, soft delete e hard delete, reaparece em outros contextos da Análise e Desenvolvimento de Sistemas, com a mesma lógica de fundo: em Banco de Dados, um soft delete costuma significar marcar um registro como removido através de uma coluna ou flag, sem apagar a linha da tabela de fato, enquanto um hard delete é a remoção definitiva da linha, através de um comando como DELETE, sem deixar nenhum rastro recuperável.

15 - Por dentro da pasta ponto git

Vale relembrar por que a pasta ponto git é chamada de oculta: por convenção, tanto no Linux quanto no Windows, arquivos e pastas cujo nome começa com ponto não aparecem por padrão num ls comum nem no explorador de arquivos, justamente para não poluir a visão do que importa no dia a dia — o próprio VS Code segue essa convenção e esconde a pasta ponto git do painel de arquivos, mesmo que ela exista ali dentro do projeto.

Vale abrir de novo essa pasta, criada pelo git init, e revisar que ela não guarda nenhum segredo complexo. O arquivo HEAD, dentro dela, pode ser lido com qualquer comando que exiba texto, e normalmente mostra uma referência a outro arquivo, algo como ref, dois pontos, refs barra heads barra main. Ou seja, o HEAD não guarda o hash de um commit diretamente, ele guarda uma referência a outro arquivo, refs barra heads barra main, que é quem de fato guarda o hash do commit mais recente daquela linha do tempo, e esse valor é exatamente o mesmo hash que aparece no topo do git log. É por isso que, a cada novo commit, é só esse arquivo da branch que muda, e o HEAD, que só aponta para ele, anda junto automaticamente.

Outro arquivo simples de ler é o config, também dentro da pasta ponto git, que guarda as configurações daquele repositório especificamente, diferente das configurações globais do Git na máquina. Num projeto recém-criado, o conteúdo costuma ser enxuto, só com uma seção core de configuração básica, mas esse arquivo ganha uma seção nova assim que um repositório remoto é conectado, como será revisado a seguir.

Depois de abrir a pasta ponto git e ver que HEAD, a referência da branch e o config são só arquivos de texto comuns, fica mais fácil responder com precisão o que é, afinal, um repositório. No sentido amplo da palavra, repositório é só isso, um lugar onde algo fica guardado, um conceito que não é exclusivo do Git. No universo do Git, o que se guarda dentro desse lugar é justamente a pasta ponto git, o histórico completo de versões de um projeto, com seus objects, refs e HEAD. Os arquivos que se edita no dia a dia não são o conteúdo guardado em si, são só o retrato de um ponto daquele histórico, extraído para a tela pelo próprio Git.

16 - GitHub, o conceito de remote, push e pull

Até este ponto, o único lugar onde o ponto git de um projeto está guardado é uma única máquina, e é exatamente aí que mora o problema: trocar de computador, formatar o HD, ou simplesmente querer usar o projeto em outro lugar significa não ter mais acesso a esse histórico. A solução é ter um outro lugar para guardar uma cópia inteira desse mesmo ponto git, de preferência acessível pela internet, e esse outro lugar é o que o Git chama de repositório remoto, sendo o GitHub justamente um serviço que oferece esse lugar de guarda na internet, hospedando o mesmo ponto git, e entendendo o mesmo formato de arquivos que qualquer ponto git local usa. Um repositório pode ter nenhum, um ou vários remotes cadastrados, e o mais comum, quando existe só um, é chamá-lo de origin.

Depois de criar um repositório vazio no site do GitHub, sem README, para não gerar conflito com o histórico que já existe localmente, o passo seguinte é avisar o Git local de que aquele endereço existe, com o comando git remote add origin, seguido da URL do repositório no GitHub, e o comando git remote com a flag -v lista os remotes cadastrados. Vale reler o arquivo config depois disso: uma seção nova aparece, com o apelido origin e a URL do remote. Esse é o ponto mais importante desta parte: git remote add não fez nenhuma mágica de rede nem gerou nenhum arquivo escondido novo, ele só escreveu essas duas linhas dentro do mesmo config que já existia. Um remote é, fisicamente, só um apelido associado a uma URL, guardado num arquivo de texto comum.

Com o remote cadastrado, o histórico local pode ser enviado para o GitHub com o comando git push, sendo que na primeira vez se usa git push -u origin main, que liga o branch local main ao branch main do remote origin, e depois disso git push e git pull sozinhos, sem mais argumentos, já sabem para onde ir. Vale revisar também o git clone, que resolve um cenário diferente: quando o repositório já existe no GitHub mas ainda não existe em lugar nenhum na máquina, o git clone, seguido da URL, baixa o repositório remoto inteiro, todo o histórico de commits, todas as branches, tudo dentro de um ponto git novo, e já cria a pasta do projeto localmente, configurando o remote origin automaticamente, sem precisar de git init nem de git remote add na mão. O caminho inverso do push, para trazer para o computador mudanças que estejam no GitHub, é o comando git pull, que busca e traz para a máquina local os commits novos que existem no remote e ainda não existem ali.

Vale reforçar a diferença entre clone e pull: git clone é o comando de primeira vez, usado uma única vez por máquina, quando o repositório local ainda não existe; git pull, em contraste, é o comando do dia a dia, usado repetidas vezes, num repositório que já foi clonado ou criado antes, só para buscar os commits novos.

17 - Autenticação com chave SSH

Para que o GitHub aceite um git push vindo de um computador, ele precisa antes confirmar que quem está mandando aquele comando realmente tem permissão sobre aquele repositório, e uma das formas mais comuns de fazer essa confirmação, sem precisar digitar usuário e senha toda hora, é por meio de um par de chaves SSH. Uma chave SSH vem sempre em duas partes, geradas juntas: uma chave privada, que nunca sai da máquina e nunca deve ser compartilhada com ninguém, e uma chave pública, feita justamente para ser entregue a terceiros, nesse caso ao GitHub. A metáfora que ajuda a fixar isso é a de um cadeado e sua chave: a chave pública é o cadeado que se entrega para o GitHub guardar, a chave privada é a única chave que abre aquele cadeado específico, e ela fica só com o usuário.

O comando ssh-keygen, com a flag -t seguida de ed25519, o algoritmo recomendado atualmente, e a flag -C seguida de um comentário, geralmente o e-mail do usuário, gera um novo par de chaves. Ao final, dois arquivos são criados, a chave privada e a chave pública com extensão ponto pub. O comando cat, seguido do caminho da chave pública, imprime o conteúdo dela na tela, para que possa ser copiado e colado no GitHub, na seção Settings, SSH and GPG keys, New SSH key. Depois disso, é possível testar se a autenticação está funcionando com o comando ssh -T git@github.com, que tenta autenticar sem executar nenhuma operação de fato, e se tudo estiver certo, o GitHub responde confirmando o nome de usuário autenticado.
